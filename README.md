# 高并发事件处理引擎（本地内存 + 本地文件）

一个可在本地直接运行的高并发事件处理引擎：用**内存**模拟事件来源与有界
队列/状态，用**本地文件**（WAL + 快照 + 待处理日志 + 死信文件）保证异常
处置与重启一致性。不依赖任何外部中间件。

- 运行示例：`go run ./cmd/demo`
- 运行测试：`go test ./...`
- 并发检测：`go test ./... -race`

---

## 1. 并发模型

```
              有界分片公平队列                每业务键串行协调器
 事件来源 ──► 高优先级层 ──► worker0 ──► keyCoordinator(actor) ──► 状态存储
(文件+offset) 普通优先级层    worker1 ──► keyCoordinator(actor)
   │       (同级各键轮转 RR)        ▲
   └─ Submit() 先写 pending.log 再入队 ┘
```

- **分片有界队列**：队列按业务键哈希分成若干分片 channel，每个分片由
  worker 消费。不同业务键天然并行。
- **每业务键 actor（强顺序）**：每个业务键有唯一的串行协调协程。同键事件
  全部进入它的 mailbox，由它按 `Seq` 排序生效：
  - 序号衔接（= 当前版本+1）：应用；
  - 序号超前（缺口）：放入该键的最小序号堆等待前驱，**投递 worker 立即
    释放、不阻塞线程**；前驱应用后在同一协程内级联处理堆中所有连续后继；
  - 序号落后：交由存储层判定为**重复**或**冲突**。

  因此“多个 goroutine 以任意顺序向同一键投递”最终都严格按 `Seq` 生效，
  不会乱序、不会重复累加。

- **在途信号量**：限制“已接收但尚未有最终结论”的事件总量。处理能力不足
  时，事件在有界队列排队；超出 `SubmitTimeout` 即触发明确背压。

## 1.1 优先级与公平调度（新增能力）

在原有“按业务键分片 + 每键串行 actor”之上，分片队列升级为**两级优先级 +
键间轮转（round-robin）**的公平调度器：

- **事件优先级**：`Event.Priority` 取 `PriorityHigh(1)` 或缺省的
  `PriorityNormal(0)`。
  - **拥塞时高优先级先消费**：只要某分片里还压着高优先级事件，普通优先级
    事件就整体等待，绝不越过高优先级被服务；
  - **只影响不同键之间的先后**：同一业务键的事件仍全部进入该键唯一协调
    协程，由它严格按 `Seq` 排序生效。同一个键先后投递的事件，无论携带
    什么优先级，最终生效顺序都与投递（`Seq`）顺序一致，幂等语义不变；
  - 优先级随事件持久化进 `pending.log` / `events.log`，停机重启后规则
    不变（重放事件仍带原优先级）。
- **按业务键公平轮转**：同一优先级内，调度器为每个非空业务键维护一个
  轮转环，**每次只从队头键取一个事件，随后把该键转到环尾**。因此单个热点
  键即使涌入海量事件，也只能与其它键**交替推进**，无法长期霸占某个 worker
  的消费能力；冷键事件在热点键只处理了少量积压时就能得到调度。
- **热点键识别**：某个业务键“队列中 + 协调器中（mailbox/缺口堆/处理中）”
  的未结论事件总数达到 `HotKeyBacklogThreshold` 时，会被列入指标快照的
  `HotKeys`，不再无声无息地拖慢全局。

> 边界说明：优先级是**严格优先**而非加权比例。高优先级持续满载时，普通
> 优先级会被推迟（并按下面的限流语义被显式拒绝），这是有意设计——高优先
> 级代表更紧急的工作；公平性保证作用在**同一优先级内部的各业务键之间**。

## 2. 背压与可观测性

- 处理能力不足时，事件**不会被静默丢弃**。`Submit` 在截止时间内拿不到队列
  空位会返回带明确类别的归一化错误：
  - `queue_full`：容量背压，等待超时（**可重试**），表示连高优先级也进
    不来的“真正容量耗尽”；
  - `priority_throttled`：**新增**。队列满且被高优先级事件占住时，普通
    优先级事件**立即**（不消耗 `SubmitTimeout`）被拒绝，原因与真正的容量
    耗尽区分开，同样**可重试**；高优先级事件不受此限流，仍会排队等待空位；
  - `stopping`：引擎停机中，事件已在持久日志里（安全重排）；
  - 以及 `invalid` / `storage` / `canceled` / `timeout`。
- `MetricsSnapshot` 在原有吞吐/积压基础上新增：
  - `ReceivedByPriority / AcceptedByPriority / RejectedByPriority`：按
    优先级（`high` / `normal`）分类的计数；
  - `QueueHigh / QueueNormal`：队列中按优先级分类的当前积压；
  - `KeyBacklog`：每个业务键的积压明细（`Queue` / `Outstanding` /
    `Total` / `Hot`）；
  - `HotKeys` / `HotKeyThreshold`：达到阈值的热点键及其积压量。

## 3. 幂等与状态冲突

- 事件用全局唯一 `ID` 去重：相同 ID 的重复投递/失败重试/重启重放都只会
  生效一次（`duplicates` 指标计数）。
- 每个业务键维护单调 `Version` 与近期已应用 ID 窗口：`Seq < 当前版本`的
  事件被显式标记为 **conflict**，状态不被覆盖（`conflicts` 指标计数），
  而不是静默吞掉或错误覆盖。

## 4. 异常链路归一化

所有来自下游/上下文/存储的错误都经 `normalize` 映射为 `engine.Error`
（带 `Kind`、操作名 `Op`、可读 `Message` 与 `Retryable()`），不直接透出
原始错误类型：

| 来源 | 归一化 Kind | 可重试 |
| --- | --- | --- |
| `context.DeadlineExceeded`（含被包装） | `timeout` | 是 |
| `context.Canceled` | `canceled` | 否 |
| Handler/存储返回普通错误 | `internal` / `storage` | 视情况 |

可重试错误按 `MaxAttempts` 与退避 `Backoff` 重试；超过次数仍失败的事件写入
**死信文件** `dead-letter.log`（含事件与归一化原因），并 Ack 以避免毒消息
永久阻塞同键后续事件。

## 5. 优雅停机与重启一致性

文件布局（位于 `DataDir`）：

| 文件 | 作用 |
| --- | --- |
| `events.log` / `events.offset` | 事件源（追加）与已确认投递偏移 |
| `pending.log` | 待处理事件日志（add/ack），Close 时压缩 |
| `state.wal` / `state.snapshot.json` | 业务状态 WAL 与周期快照 |
| `dead-letter.log` | 最终放弃事件及其归一化原因 |

停机两阶段：

1. 关闭接收（Submit 返回 `stopping`）、停止事件源；
2. 在 `ShutdownTimeout` 内等待排空（队列深度、在途信号量、每键 mailbox 与
   缺口堆全部归零）；随后关闭队列与协调协程并统一 fsync 落盘。
   - 超时未完成的事件**不 Ack**，保留在 `pending.log` 中；
   - 下次 `Start` 重放 `pending.log`，配合存储层幂等，做到**已有状态不
     丢失、事件不重复应用**。

事件源只在 sink（进入引擎）成功后推进 offset；下游拒绝/崩溃不推进，重启
从断点重读，配合幂等实现至少一次投递 + 精确一次生效。

> 优先级与公平调度的状态（两级队列、键轮转环、热点计数）全部是**内存态**，
> 唯一新增的持久信息是事件上的 `priority` 字段（已随事件 JSON 落盘，旧文件
> 缺省该字段时按普通优先级解析）。因此停机排空、`pending.log` 压缩与重启
> 重放流程与之前完全一致：未 Ack 事件（含其优先级）安全重放，不会破坏既有的
> 排空与一致性保证。

## 5.1 重启恢复与运行期限流规则的边界

恢复（`Start` 重放 `pending.log`）不是接收新工作，而是把**已落盘的存量**
排空，因此刻意不套用运行期的拒绝/背压规则：

- **不受优先级限流**：恢复事件入队走恢复专用入口，永远不会得到
  `priority_throttled` / `queue_full`。即使上次停机时遗留的积压超过单个
  分片容量、且高/普通优先级混合，`Start` 也必须把全部存量放回队列并启动
  成功——不允许“高优先级积压多就把普通优先级恢复事件挡在门外”，更不能
  把这种拒绝当成致命错误让启动失败。
- **不占在途信号量**：恢复事件投递到各键协调器时不占用 inflight 信号量
  （信号量是运行期背压手段）。否则恢复期优先级反转（高优先级的大序号先
  进入缺口堆等待前驱）会让缺口等待事件耗尽槽位、前驱滞留队列无法投递，
  造成恢复期死等。mailbox 容量本身仍对恢复事件形成有界缓冲。
- **一致性结论**：无论遗留积压多大、优先级怎么混，恢复完成后各业务键的
  终态与“一直跑到停机、不重启”完全一致；同一业务键在恢复期内仍严格按
  投递（`Seq`）顺序生效，重复投递/重放由存储层幂等判重，不会重复生效；
  多 worker、多业务键并发恢复不漏、不重、不死等。
- **运行期规则不变**：上述豁免只作用于恢复链路。正常投递的优先级限流
  （`priority_throttled`）、容量背压（`queue_full`）、幂等去重与停机排空
  语义保持原样；恢复积压回落到容量内之前，运行期 `Submit` 照常等待/拒绝。

## 6. 持久化级别（配置项 `SyncEachWrite`）

- `true`（默认）：每次确认通过组提交 `fsync`，操作系统崩溃也不丢已确认
  状态（沙箱磁盘 fsync 较昂贵，绝对吞吐受限）。
- `false`：WAL/日志采用微小时长（亚毫秒~毫秒）的组提交，吞吐显著更高；
  OS 崩溃可能丢失最近未落盘窗口内的数据，但事件源 offset 未推进，重启会
  重新投递，存储幂等保证结果一致；优雅停机会完整落盘。

## 7. 配置项（`engine.Config`）

| 字段 | 含义 | 默认 |
| --- | --- | --- |
| `DataDir` | 本地文件目录 | `data` |
| `Workers` | 队列分片/worker 数（向上取 2 的幂） | CPU 核数 |
| `QueuePerShard` | 每个分片有界队列容量 | 1024 |
| `MailboxPerKey` | 每业务键协调器 mailbox 容量 | 256 |
| `SubmitTimeout` | 队列满时 Submit 最长等待 | 50ms |
| `HandleTimeout` | 单事件处理截止 | 1s |
| `MaxAttempts` | 可重试错误最大尝试次数 | 3 |
| `Backoff` | 重试基础退避（第 n 次 n×Backoff） | 5ms |
| `ShutdownTimeout` | 优雅停机最长等待 | 5s |
| `SyncEachWrite` | 是否逐次 fsync（组提交） | true |
| `HotKeyBacklogThreshold` | 单键积压达到该值即判定为热点键并列入 `HotKeys` | 128 |

事件字段 `Event.Priority`：`0=PriorityNormal`（缺省）、`1=PriorityHigh`；
传入其它值一律归一化为普通优先级。

## 8. 测试覆盖

- 并发竞争下总量精确、不重不漏（独占键 + 同键高并发乱序）；
- 同键事件严格按 `Seq` 生效；
- 重复投递幂等、乱序事件显式冲突不覆盖；
- 容量背压以可区分原因拒绝并计入指标；停机期间拒绝为 `stopping`；
- 超时/取消/普通错误归一化为可分类别；可重试错误重试后进死信；
- 优雅停机后重启：状态不丢、pending 重放幂等、事件源 offset 断点续读。
- **优先级与公平性（新增，`scheduling_test.go`）**：
  - 拥塞时高优先级先于更早投递的普通优先级被消费；
  - 同键“高优先级后继 + 普通优先级前驱”乱序/混优先级投递，最终仍严格按
    `Seq` 生效（同键顺序与幂等不被优先级打乱）；
  - 热点键大量涌入时冷键不被饿死（在热点键只推进部分积压时即被调度）；
  - 热点键达到阈值后进入 `HotKeys`，`KeyBacklog` 按键可见；
  - 队列被高优先级占满时，普通级立即得到 `priority_throttled`、高优先级
    超时得到 `queue_full`，两种原因及按优先级计数都可区分；
  - 队列积压按 `high/normal` 分别可观测；
  - 混优先级事件在短超时停机 + 重启重放后结果精确一致。
- **重启恢复链路（`recovery_test.go`）**：
  - 停机遗留“高/普通混合、超过单分片容量”的积压时，重启启动成功、存量
    全部消化，终态与“不重启直接跑完”逐键一致（单分片确定性复现 +
    多 worker/多键并发恢复两种场景）；
  - 恢复期内各业务键严格按 `Seq` 有序生效，不漏事件、不重复生效、不死等；
  - 恢复不受 `priority_throttled` / `queue_full` / 在途信号量限制，运行期
    限流与背压拒绝语义保持不变。
- 全部用例在 `go test ./... -race` 下稳定通过，单测日志打印关键输入与
  判定依据（版本、值、指标分类）。

## 9. 本地验证

```bash
go run ./cmd/demo      # 运行示例：观察 queue_full 背压、热点键识别、分级积压
go test ./...          # 运行全部单测
go test ./... -race    # 并发检测（推荐）
# 只跑优先级与公平性新增用例（可加 -count=N 反复验证稳定性）：
go test ./engine -race -run 'TestPriority|TestSameKeyPriority|TestFair|TestHotKey' -count=10 -v
# 只跑重启恢复链路用例（大积压 + 混优先级 + 多键并发恢复）：

```
